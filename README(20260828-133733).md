# CPU Scheduler Simulator

A C++17 CPU scheduling simulator implementing six classical scheduling
algorithms, a common simulation interface, performance metrics,
concurrent execution, and an algorithm recommendation engine.

## Features

-   **Six scheduling algorithms:** FCFS, RR, SRT, SPN, HRRN, and MLFQ
-   Gantt timeline generation
-   Process-level metrics: Completion Time, Turnaround Time, Waiting
    Time, and Response Time
-   Workload-level metrics: Average Waiting Time, Average Turnaround
    Time, Average Response Time, CPU Utilization, and Throughput
-   Sequential and concurrent simulation execution
-   Thread-safe job queue and result collection using `std::thread`,
    `std::mutex`, and `std::condition_variable`
-   Recommendation engine that ranks algorithms using normalized
    performance metrics
-   Reproducible benchmark workload generation
-   Makefile-based build and benchmark commands

## Project Architecture

The simulator is designed around an abstract `Scheduler` interface. Each
scheduling algorithm provides its own implementation of `simulate()`
while sharing the same process model, timeline representation, metrics
engine, execution infrastructure, and recommendation engine.

``` text
                         Scheduler (abstract)
                               |
          +--------------------+---------------------+
          |         |          |        |      |     |
         FCFS       RR        SRT      SPN   HRRN   MLFQ
          |         |          |        |      |     |
          +---------+----------+--------+------+-----+
                               |
                           Simulation
                               |
                            Metrics
                               |
                    +----------+----------+
                    |                     |
              Sequential            Concurrent
                                          |
                                  Job Queue + Workers
                                  mutex + condition_variable
                                          |
                                  Results Collector
                                          |
                                  Recommendation Engine
                                          |
                                  Best Algorithm
```

### Design Choices

The project uses several important object-oriented and concurrency
design principles:

-   **Abstraction:** `Scheduler` defines a common interface for all
    scheduling algorithms.
-   **Polymorphism:** all algorithms can be handled through `Scheduler`
    pointers.
-   **Single Responsibility:** scheduling, timeline construction,
    metrics calculation, simulation execution, and recommendation are
    separated into different components.
-   **Open/Closed Principle:** a new scheduler can be added by
    implementing the `Scheduler` interface without rewriting the core
    runner.
-   **RAII:** `std::unique_ptr` manages scheduler objects automatically.
-   **Thread safety:** the concurrent runner protects shared data with
    mutexes and coordinates workers using a condition variable.

## How to Run

### Run the Scheduler

Build the main simulator:

``` bash
make
```

Run it:

``` bash
./scheduler
```

Or combine both:

``` bash
make && ./scheduler
```

The scheduler runs the configured algorithms concurrently and prints
their timelines, process metrics, performance summaries, and
recommendation ranking.

### Run the Benchmark

Build the benchmark:

``` bash
make benchmark
```

Run it:

``` bash
./benchmark
```

Or combine both:

``` bash
make benchmark && ./benchmark
```

The benchmark compares sequential and concurrent execution using the
same scheduling implementations.

### Clean

``` bash
make clean
```

The recommendation depends on the current workload, so a different
process set can produce a different ranking.

## Concurrent Execution

The simulator supports running independent scheduling simulations
concurrently.

Instead of:

``` text
FCFS -> RR -> SRT -> SPN -> HRRN -> MLFQ
```

the concurrent runner places scheduler jobs into a shared queue and uses
worker threads to process them.

``` text
                 Job Queue
                     |
        +------------+------------+
        |            |            |
     Worker 1     Worker 2     Worker N
        |            |            |
     Scheduler    Scheduler    Scheduler
        |            |            |
        +------------+------------+
                     |
              Results Collector
```

The job queue is protected by a mutex, a condition variable coordinates
worker threads, and a separate mutex protects result collection.

The number of workers is limited to the smaller of the number of
scheduler jobs and the hardware concurrency reported by the system.

Because the simulations are independent, this is a natural task-level
parallelism problem. Concurrent execution reduces total wall-clock time
for sufficiently large workloads.

## Why the Concurrent Version Is Faster

Each algorithm receives the same workload but maintains its own local
simulation state. Therefore, the six simulations do not need to wait for
one another.

``` text
Sequential:

FCFS -> RR -> SRT -> SPN -> HRRN -> MLFQ
             Total time = sum of job times


Concurrent:

FCFS ────────┐
RR ──────────┤
SRT ─────────┤
SPN ─────────┤ -> worker threads execute independent jobs
HRRN ────────┤
MLFQ ────────┘

             Total time ≈ parallel workload
                         + thread/synchronization overhead
```

The speedup is not expected to equal the exact number of CPU cores
because thread creation, synchronization, OS scheduling, and differences
in algorithm runtime all contribute overhead.

## Algorithms

| Algorithm | Full Form | Type | Main Idea |
|-----------|-----------|------|-----------|
| **FCFS** | First Come, First Served | Non-preemptive | Execute processes in arrival order |
| **RR** | Round Robin | Preemptive | Give each ready process a fixed time quantum |
| **SRT** | Shortest Remaining Time | Preemptive | Always run the process with the shortest remaining burst |
| **SPN** | Shortest Process Next | Non-preemptive | Select the shortest available burst time |
| **HRRN** | Highest Response Ratio Next | Non-preemptive | Select using `(waiting + burst) / burst` to balance waiting time and burst length |
| **MLFQ** | Multilevel Feedback Queue | Preemptive | Use multiple priority queues with feedback between levels |

## Metrics

### Process Metrics

-   **Completion Time (CT):** time at which the process finishes.
-   **Turnaround Time (TAT):** `CT - Arrival Time`.
-   **Waiting Time (WT):** `TAT - Burst Time`.
-   **Response Time (RT):** first execution time minus arrival time.

### Workload Metrics

-   **CPU Utilization:** percentage of elapsed time during which the CPU
    executes processes.
-   **Throughput:** number of completed processes per unit of elapsed
    time.
-   **Average metrics:** arithmetic mean across all processes.
